## The question

Horizon 2's deliverable is "linear regression converges on CPU through library
calls alone" (GOAL.md §Horizon 2). The _scoping_ question is: does that
convergence proof flow through a reusable `gradus:train` contract (Option A),
or does it carry its loop inline as an exemplum-only proof that exercises the
library boundary for forward, backward, loss, and optimizer calls while the
iteration structure stays demo-local (Option B)?

SCOPE.md finding #2 identified a sequencing gap: "Linear regression converges
on CPU through library calls alone" needs a minimal training consumer, but
`train` is scheduled at Horizon 7. The gap is real. The decision frames
whether we close it now (with a reusable contract the compiler can't yet
execute) or explicitly defer the reusable loop to Horizon 7.

## Compiler constraints (U1 evidence)

Unit U1 produced a live gradient-seam fixture. It discovered three compiler
capabilities that block a reusable `gradus:train` contract today — not one as
the original plan assumed (SEM010), but three independent blockers. All three
are verified against actual `faber check` / `faber run` output from U1.

| # | Constraint | Error text / evidence | Owner |
| --- | --- | --- | --- |
| SEM010 | Tensor-returning function calls inside loops are blocked. The compiler rejects `functio` calls that return `tensor<f32, [M,N]>` inside `itera` bodies. Exempla inline the forward pass in `incipit` as a workaround. | `examples/training/linear-regression/src/train.fab:91-95`: "Forward pass (inlined — function call inside loop triggers SEM010 in current compiler for tensor-returning functions)." | Radix |
| SEM004 | Companion functions generated by `@ radix backward` are file-scoped. They are not exported through `importa` boundaries. A consumer importing `gradus:gradient` cannot call `loss_backward` across the import — it must mirror the annotation locally. | `gradus/exempla/gradient-seam/src/main.fab:4-6`: "The consumer has its own @ radix backward annotation because compiler-generated companions are file-scoped and not exported through importa boundaries." | Radix |
| LIB-MIR | `faber run -t fmir` does not support library imports. The MIR lowering path rejects packages that import `gradus:*` modules. `faber check` passes (proving the import DAG is valid), but the run path fails with a package-MIR error. | `gradus/exempla/gradient-seam/src/main.fab:7-8`: "faber run -t fmir fails for library-importing packages." Error text: `error: package MIR does not yet support library imports such as gradus:gradient`. | Radix / Faber |

These three constraints are independent. Fixing one does not fix the others.
A reusable `gradus:train` module needs all three resolved: the consumer must
be able to `faber run` a package that imports `gradus:train` (LIB-MIR), the
train module must be able to call the companion backward across the
`gradus:gradient` import boundary (SEM004), and the loop body must be able to
call the forward function — which returns a tensor — from inside `itera`
(SEM010).

## Option A: Reusable `TrainStep` contract (in `gradus:train`)

Define a minimal training-loop contract in `gradus:train`. A genus or free
function carrying the signature `(params: P, batch: Batch, lr: f32) → P`. The
training loop owns the iterate-until-convergence structure (epoch count, loss
tracing, metric collection). The consumer provides params + loss function;
`train` provides the loop skeleton.

The JAX-shaped framing (GOAL.md lines 203–229) is the design target: pure
functions, explicit params, stateless loop. `gradus:train` would own the
iteration while remaining model-independent — it calls the consumer's forward
and backward through type parameters.

### Pros

- Proves the library boundary for training. A consumer defines a model; the
  library trains it. This is the JAX-shaped architecture working end to end.
- Reusable for Horizon 3+ when more model families (MLP, transformer) appear.
  One contract, many consumers.
- Resolves the SCOPE.md sequencing-gap finding directly: `train` at Horizon 2
  rather than Horizon 7, compressing the delivery schedule.
- Matches the dependency DAG: `gradus:train` sits below Horizon 7 workloads
  but is structurally independent of them.

### Cons

- **Not executable on the current toolchain.** Three independent compiler
  capabilities must ship before a consumer can `faber run` a training workload
  through `gradus:train`:
  1. LIB-MIR: `faber run -t fmir` must support library imports.
  2. SEM004: Companion functions must be exportable through `importa`.
  3. SEM010: Tensor-returning function calls must be legal inside `itera`.
  Until all three ship, Option A is a contract document that cannot be proven
  through execution. The U1 fixture proved `faber check` passes (import
  resolution works), but `faber run` fails — the check path is not sufficient
  for a training proof.
- `gradus:train` depends on `gradus:loss` and `gradus:optimize` per the DAG
  and the current stub. Those modules don't exist yet at Horizon 2. Building
  `train` before its dependencies risks the contract encoding assumptions
  about loss/optimizer signatures that the implementation can't validate.
- Premature abstraction: the one training consumer is linear regression.
  Without a second consumer (MLP at Horizon 4), the contract can't be
  validated for generality. The current exemplum inlines its loop — extracting
  a generic loop before a second caller exists risks over-engineering.

## Option B: Exemplum-only proof (recommended)

The Horizon 2 linear-regression proof carries its own loop inline, matching
the pattern in `examples/training/linear-regression/src/train.fab`: forward
ops inlined in `incipit`, companion backward called per step, SGD update
inlined. The proof exercises the library boundary for the critical calls —
`gradus:tensor` for construction and ops, `gradus:gradient` for the companion
backward (mirrored annotation, per SEM004 workaround), `gradus:loss/mse` for
loss computation, `gradus:optimize/sgd` for the parameter update — while the
loop structure (the `itera` body) stays demo-local. The reusable loop is
deferred to Horizon 7, when `gradus:train` is already scheduled and the three
compiler capabilities are expected to ship.

### Pros

- Ships Horizon 2 on the current compiler. No compiler fix dependency. The
  linear-regression exemplum compiles, runs, and produces a convergence proof
  today — matching the existing `examples/training/linear-regression/` pattern
  that already `faber check` + `faber run -t fmir` passes.
- Proves the critical seams: gradient wrapper (U1), loss function, optimizer
  step. The inline loop is orchestration — the library calls are the
  architecture proof. The loop structure is not in scope for Horizon 2 per the
  GOAL acceptance criterion ("linear regression converges on CPU through
  library calls alone" — the library calls are tensor, gradient, loss,
  optimizer).
- No premature abstraction. The loop is extracted to `gradus:train/loop` when
  a second consumer (MLP at Horizon 4 or nanoGPT at Horizon 7) demonstrates
  the contract shape. The inline loop is honest about what the compiler can
  execute.
- Matches precedent: the existing linear-regression exemplum already does this
  pattern — inlined forward, companion backward per step, inlined SGD. Option
  B swaps the raw `@ radix backward` annotation for `gradus:gradient` import
  plus the mirrored-annotation workaround (the SEM004 constraint documented
  by U1).
- The SCOPE.md sequencing gap is acknowledged honestly rather than papered
  over by a contract the compiler can't execute.

### Cons

- Doesn't prove the train-library boundary. The first proof doesn't exercise
  `gradus:train`. A future extraction from exemplum to library will require
  refactoring — the loop body must be lifted from the exemplum's `incipit`
  into a reusable genus or function.
- The exemplum carries a mirrored `@ radix backward` annotation (SEM004
  workaround), which means the `gradus:gradient` import is partial — the
  forward call comes from the library, but the backward companion is
  file-local. This is honest but visually noisy.
- Horizon 7 already has `train/loop` scheduled. If three more horizons pass
  before the loop is extracted, the inline pattern may drift across exempla
  (linear regression, MLP, attention proof), creating multiple extraction
  points rather than one canonical loop.

## Recommendation: Option B

Option B is the only executable path on the current toolchain. Option A is
blocked on three independent compiler capabilities (LIB-MIR, SEM004, SEM010),
none of which have committed ship dates. Building a reusable contract that
can't be proven through execution is premature architecture — it violates the
GOAL.md invariant that "a capability claim requires an executable workload
and negative evidence."

The Horizon 2 goal is "linear regression converges on CPU through library
calls alone." The library calls are `gradus:tensor`, `gradus:gradient`,
`gradus:loss/mse`, `gradus:optimize/sgd`. The loop structure is orchestration,
not library surface. Option B proves every library seam that Horizon 2
requires while staying on a compiler path that works today.

### Gates for future Option A extraction

The three compiler capabilities below are the trigger for re-evaluating a
reusable `gradus:train` contract. When all three ship, an extraction from the
Horizon 2 linear-regression exemplum (and any subsequent inline-loop exempla)
to `gradus:train/loop` becomes a delivery unit, not a research spike.

| Gate | What must be true | Owner | Re-evaluation trigger |
| --- | --- | --- | --- |
| LIB-MIR | `faber run -t fmir gradus/exempla/gradient-seam/` exits 0 with `nota` output. The MIR lowering path accepts packages that import `gradus:*` modules. | Radix / Faber | A consumer importing `gradus:gradient` can `faber run` without error. |
| SEM004 | A consumer importing `gradus:gradient` can call `loss_backward` through the import boundary — no mirrored `@ radix backward` annotation in the consumer file. Companion functions are exportable through `importa`. | Radix | U1 fixture passes with `gradient.loss_backward(...)` replacing the local `@ radix backward` mirror. |
| SEM010 | A `functio` returning `tensor<f32, [M,N]>` can be called inside an `itera` body. The forward pass can be extracted into a named function rather than inlined in `incipit`. | Radix | The linear-regression exemplum compiles with a factored `functio forward(params, x) → tensor<...>` call inside the loop body. |

Gating note: these are sequenced, not parallel. LIB-MIR gates whether a
consumer can run at all. SEM004 gates whether the backward companion crosses
the import boundary. SEM010 gates whether the loop body can call tensor-returning
functions. The extraction to `gradus:train` becomes viable only after all three
clear.
