# Tensor Genus + Param-Record Contract

**Status**: decided
**Date**: 2026-08-01
**Author**: Hand (delivery agent, unit U2)
**Lowers from**: [checkpoint-plan.md](checkpoint-plan.md) §U2 + [SCOPE.md](SCOPE.md) gate register
**Grounds**: U1 gradient-seam fixture evidence + compiler ground truth

## U1 evidence

The gradient-seam fixture compiled and executed. Two signatures are ground
truth for this contract:

**Forward** (`gradus:gradient`):

```text
@ radix lane "air"
@ radix backward "loss_backward"
functio simple_loss(tensor<f32, [2,2]> x, tensor<f32, [2,2]> w) → f32
```

The forward function composes raw AIR tensor types. No `genus Tensor` wrapper.
The compiler rejected genus wrapping of AIR tensor types (`genus Tensor { data
sponte tensor<f32,[2,2]> }` → PARSE001). The public value representation is
raw `tensor<f32, [N,M]>`.

**Backward** (compiler-generated companion):

```text
loss_backward(x, w, nil(), upstream: f32) → iuncta(grad_x, grad_w)
```

Consumer destructured: `fixum [_, gw] ← loss_backward(x, w, nil(), 1.0)`.

**Execution path**: The U1 execution proof is self-contained. `faber run -t
fmir` does not support library imports — the consumer cannot build against
`gradus:gradient` and run through `faber run`. Execution proofs live in
self-contained exempla. Library compilation is verified through `faber check`.
This is the current compiler boundary; it does not weaken the contract — it
defines what a consumer can prove today.

**Companion scope** (SEM004): Companion functions generated by `@ radix
backward` are file-scoped and not exportable through `importa`. A consumer
importing `gradus:gradient` can call `simple_loss` but cannot call
`loss_backward` across the import boundary. Gradients must be produced and
consumed in the same compilation unit that owns the `@ radix backward`
annotation.

## Contract dimensions

### 1. Shape encoding

**Decision**: Static rank in type annotations; runtime shape inspection.

Raw AIR tensor types carry static rank at the type level: `tensor<f32,
[N,M]>`, `tensor<f32, [B,T,C]>`. The rank is fixed at compile time and the
compiler enforces rank consistency across operations. Runtime shape is dynamic
— `magnitudines()` returns `lista<numerus>` and individual dimensions can vary
within the static rank.

**Horizon 1 rule**: Fixed static shapes only. A model function declares its
parameter and input shapes at the type level. Reshaping within a fixed rank
(e.g., `[B*T, C]` for attention projection) is permitted; rank-changing
reshapes are not. Dynamic-rank tensors (where the rank itself varies at
runtime) are deferred until a concrete consumer demonstrates the need.

**Horizon 2+ path**: Static rank remains the default. Dynamic batch dimension
is addressed by the batch contract in `gradus:data` — batching stacks
fixed-shape samples into a leading batch dimension. The tensor genus does not
carry batch-vs-unbatched mode; the model function signature reveals it.

**Compiler ground truth**: The AIR type system enforces `tensor<dtype,
[dims...]>` at the type level. The `magnitudines()` runtime accessor bridges
static rank and dynamic dimension sizes. This is the U1-compiled reality.

### 2. Dtype enumeration

**Decision**: `f32` only for Horizon 1–2; path to `f64` and `i32`; dtype is
type-level, not a runtime tag.

The tensor type is `tensor<f32, [...]>`. There is no runtime `dtype` field and
no runtime dtype dispatch. The dtype is part of the type annotation. Mixed
dtype operations are a compile-time error.

**Horizon 1–2**: `f32` exclusively. All differentiable tensor ops in the AIR
transform are exercised on f32. Loss functions and optimizers use f32. The
linear regression proof uses f32.

**Horizon 3+**: `f64` for gradient-sensitive numerics (e.g., the FD oracle
epsilon, high-precision loss computation). Added as a separate type
(`tensor<f64, [...]>`) when a concrete numeric-stability consumer demands it.
No implicit f32↔f64 coercion — explicit cast only.

**Horizon 5+**: `i32` for indexing and embedding lookup (token IDs, position
indices). The embedding table itself remains f32. Integer tensors are
non-differentiable; `@ radix backward` on a function accepting `tensor<i32,
[...]>` treats integer arguments as frozen.

**Compiler ground truth**: The runtime tensor is generic `Tensor<T>`. The AIR
type system supports `tensor<f32, ...>`, `tensor<f64, ...>`, and
`tensor<i32, ...>`. The AD transform handles f32 and f64. i32 is treated as
non-differentiable.

### 3. Ownership

**Decision**: Value semantics with move-on-assign; JAX-shaped pure functions.

`tensor<f32, [N,M]>` is an owned value type. Assignment with `←` moves
ownership. Dual use requires explicit clone (the `replica` method or
equivalent). There is no reference counting at the source level.

The JAX-shaped model applies: parameters go in as owned tensors, new
parameters come out:

```text
functio train_step(params: GptParams, batch: Batch, lr: f32) → GptParams {
    // params consumed by forward; new params returned
}
```

The `Arc<Mutex<Vec<T>>>` in `faber-runtime/src/tensor.rs` is generated-code
machinery — the runtime owns the reference count for execution, not the source
contract. The source-level contract is pure value semantics.

**Horizon 1 rule**: No `ref` or borrow syntax in Faber today — values are
always moved or cloned. The contract reflects this: the gradient wrapper
consumes parameter tensors (they're moved into the `@ radix backward` call)
and the companion returns gradient tensors as new values. The optimizer
consumes params and grads, returns new params. This is exactly what compiled
in U1.

### 4. Error behavior

**Decision**: Compile-time shape checking where rank is static; runtime error
on shape mismatch; no `Result` return type.

Faber has no sum types for error handling. There is no `Result` or `Option` in
the type system. Errors surface as compile-time diagnostics (type-rank
mismatches, missing fields) or runtime error constants.

**Compile-time**: Static rank mismatches are caught by the compiler (e.g.,
passing `tensor<f32, [2,2]>` to a parameter expecting `tensor<f32, [3,3]>`).
Dimension-size mismatches within the same rank are runtime errors because
dimension sizes are dynamic at the AIR level.

**Runtime**: Shape mismatches follow faber-runtime `ERR_*` convention (e.g.,
`ERR_TENSOR_SHAPE_MISMATCH` string constant). The runtime panics on
irrecoverable shape errors — there is no error-propagation channel in the type
system.

**FD/gradient comparison**: The U1 fixture uses `nota` for diagnostic output
and inline comparisons with explicit tolerance checks (`dif0 ← fd0 -
flat_gw[0]`). This is the contract's error-reporting pattern: the consumer
inspects values and emits verdicts through `nota`, not through a
library-provided error type.

**Horizon 2+**: If the compiler later supports a compile-time dimension
tracking pass (const-generic dimensions), the error boundary shifts further
left. Until then, static rank + runtime dimension checking is the contract.

### 5. Dispatch-neutral seam

**Decision**: No device handles, buffer objects, or backend tags in public
values. Radix chooses lowering target from build configuration, not tensor
metadata.

`tensor<f32, [N,M]>` is pure math — shape + dtype + data. The type carries no
device identifier, no memory buffer handle, no backend execution tag. The
device boundary is below the Gradus source level:

```text
Gradus source (device-neutral)
  → Radix lowering (chooses CPU/GPU target)
    → Host backend (executes on device)
```

**Compiler ground truth from U1**: Execution proofs are self-contained
exempla. `faber run -t fmir` targets the fmir interpreter (CPU). GPU execution
is a mir-swarm rung owned by Radix + hosts. Gradus source compiles identically
for both paths — the device choice is a build-target decision, not a tensor
property.

**Horizon 1 rule**: No `Device` parameter, no `Backend` enum, no
`CpuTensor`/`GpuTensor` split. A single tensor type serves both execution
paths. If a future host needs device placement hints, they live in faber.toml
build configuration or a host execution profile, not in the tensor genus.

### 6. Param-record contract

**Decision**: Flat genus with named `tensor<f32, [...]>` fields; optimizer
consumes `(params: P, grads: P) → P`; field-wise update; per-genus handwriting
for Horizon 1–2 model families.

A parameter record is a flat genus — no nesting, no generic type parameters,
no reflection:

```text
genus LinearParams {
    sponte tensor<f32, [C_in, C_out]> w
    sponte tensor<f32, [C_out]> b
}
```

The optimizer signature is generic over the record genus:

```text
functio sgd_step(genus LinearParams params,
                 genus LinearParams grads,
                 f32 lr) → genus LinearParams {
    fixum tensor<f32, [C_in, C_out]> new_w ←
        params.w.subtrahe(grads.w.multiplica_scalari(lr))
    fixum tensor<f32, [C_out]> new_b ←
        params.b.subtrahe(grads.b.multiplica_scalari(lr))
    redde { w: new_w, b: new_b }
}
```

The update is handwritten field-by-field. The optimizer body knows the genus
structure. Per SCOPE soft-gate: "per-genus handwriting is sufficient for 1–2
model families." This is the Horizon 1–2 reality — `LinearParams` and
`MlpParams` (for the MLP proof in Horizon 3) are hand-maintained.

**Companion-scope constraint (SEM004)**: The `@ radix backward` companion is
file-scoped and not exportable through `importa`. The gradient companion only
lives in the compilation unit that owns the `@ radix backward` annotation.
This means:

- `gradus:gradient` exports the forward wrapper (`simple_loss`), but the
  companion (`loss_backward`) is invisible to consumers importing
  `gradus:gradient`.
- Gradients must be produced inside `gradus:gradient` (where `@ radix
  backward` lives). The optimizer call site produces gradients by calling a
  Gradus function that internally runs the companion and returns the gradient
  record.
- The "wrapping" shape for Horizon 2: `gradus:gradient` exports a function
  that takes params + input, runs forward + companion backward, and returns
  `(loss, grads)`. The consumer calls this function and passes the grads to
  the optimizer. The companion never crosses the `importa` boundary.

  ```text
  // Consumer's training step:
  fixum [loss, lineari_grads] ← gradient.calcula_et_retro(lineari_params, input)
  fixum lineari_params ← optimizer.sgd_step(lineari_params, lineari_grads, lr)
  ```

**Gradient struct shape**: The companion produces an `iuncta` flat tuple (U1
evidence). For a parameter record with named fields, the wrapper in
`gradus:gradient` destructures the companion iuncta and packs the result into
the matching gradient-record genus. The consumer never destructures the raw
companion iuncta.

**Horizon 7+**: If a third model family (transformer) makes handwriting
painful, revisit generic field-mapping. The contract does not pre-build it —
the soft gate is explicit that handwriting is sufficient for the first proofs.

## Future compiler capabilities that would change this contract

| Capability | Current limitation | Contract dimension affected | Horizon to revisit |
| --- | --- | --- | --- |
| Genus wrapping of AIR tensor types | `genus Tensor { ... }` → PARSE001 | 1 (shape), 6 (param record fields become `Tensor` instead of raw `tensor<f32, [...]>`) | When compiler supports it; U1 finding recorded |
| Companion function export through `importa` | SEM004 — companions are file-scoped | 6 (gradient production moves to consumer side) | When compiler lifts scope restriction |
| `faber run` with library imports | `faber run -t fmir` cannot resolve `gradus:*` imports | 5 (execution proofs shift from self-contained exempla to library-consuming packages) | When MIR lowering supports provider resolution at run time |
| Compile-time dimension tracking | Dimension sizes are runtime only | 4 (shape errors shift from runtime to compile time) | See const-generic dimension pass |
| Generic field-mapping for record genera | No reflection or generic field access in Faber | 6 (optimizer generalizes over any param record) | Horizon 7+ per SCOPE soft gate |
